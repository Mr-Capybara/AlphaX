# 开发与协作规范

本目录用于后续 Codex / agent 协作者接手阅读。

## 版本控制

- 修改前先确认工作区状态，注意区分用户改动、上游仓库改动和本次 agent 改动。
- 不要跨仓库混改：各子项目仓库和顶层项目文档应分别看待。
- 父仓库只管理顶层文档和自己的方法；各基线方法由各自仓库管理。
- 探索某个基线方法的改动时，从该方法用于复现的基线提交创建实验分支，在该方法自己的仓库中修改和提交。探索阶段的改动留在实验分支；确认选用某个方案作为自研方法后，再将选定的实现纳入 `methods/Ours/`。
- 临时实验产物、日志、缓存不要随手加入长期文档或源码。

## 代码变更

- 优先做最小必要改动，避免无关重构。
- 不要把一次性探索代码混入核心模块；实验代码应有清晰边界。

## 文档分工

- `PLAN.md`：阶段计划，只能在人类确认后写入或调整。
- `STATUS.md`：当前执行状态，说明 PLAN 已完成到哪一步，可由 agent 更新。
- `TODO.md`：下一步行动，对应 PLAN 中尚未完成的某一步，可由 agent 更新。
- `DECISIONS.md`：技术决策记录，只记录迭代中已经形成的明确决策。
- `EXPERIMENTS.md`：实验记录和实验索引，不写大段原始日志。
- `HISTORY.md`：归档已经落地完成的 PLAN。

## PLAN / STATUS / TODO 关系

- `PLAN.md` 是阶段性、人审后的计划，可以包含若干步骤。
- `STATUS.md` 只记录当前完成到 PLAN 的哪一步，以及必要的简要说明。
- `TODO.md` 只记录下一步具体行动，通常对应 PLAN 的下一步。
- 完成一个 PLAN 后，先归档到 `HISTORY.md`，再由新的已确认 PLAN 覆盖 `PLAN.md`。
- 不要在三个文件里重复同一段背景说明。

## 实验与决策记录

- 每个实验至少记录目的、配置、输入、结果位置、结论。
- 结论必须能追溯到具体运行结果。
- 不要把未经验证的观察写成技术决策。
